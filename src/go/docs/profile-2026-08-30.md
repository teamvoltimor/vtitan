## Measured (Go)

### Microbenchmarks

Command (the `-bench=.` value must be quoted in PowerShell, else Go parses `.`
as a package path):

```powershell
go test "-bench=." -benchtime=50x ./internal/sim/scenario/ ./internal/nav/navigator/
```

At the plan's `-benchtime=50x`:

| Benchmark | ns/op (50x) |
|-----------|-------------|
| `BenchmarkScenarioStep-16` | 21344 |
| `BenchmarkNavigatorStep-16` | 59562 |

**The 50x navigator number is not trustworthy.** At 50 iterations it is
dominated by first-call warmup (lazy init, page faults, branch/cache cold
start). Re-running at `-benchtime=2000x -benchmem -count=3`:

| Benchmark | ns/op (2000x, 3 runs) | B/op | allocs/op |
|-----------|----------------------|------|-----------|
| `BenchmarkScenarioStep-16` | 31891 / 29582 / 25296 | 3072 | 1 |
| `BenchmarkNavigatorStep-16` | 7947 / 3675 / 6396 | 1129 | 7 |

Steady-state readings to quote: **scenario step ≈ 25–32 µs**, **navigator step
≈ 4–8 µs**. Run-to-run spread is wide (navigator varies >2x) because this is an
unpinned, non-quiesced workstation; treat these as order-of-magnitude, not
p50/p99. A real p50/p99 distribution needs per-step timestamps on a quiet host,
which neither the benchmarks nor the harness currently emit.

### Harness + pprof

```powershell
# NOTE: /tmp does not exist on Windows; substitute a real temp dir.
go run ./cmd/bench-harness --steps 500 `
  --cpuprofile $env:TEMP\go_cpu.prof --memprofile $env:TEMP\go_mem.prof
```

- `--steps 500` → **500 steps in 15.75 ms (31504.8 ns/op, 31741 steps/s)**.
- At 500 steps the CPU profile captured only **10 ms / 1 sample** - useless for
  hotspot attribution. Re-ran at `--steps 200000` for the profile below:
  **200000 steps in 5.176 s (25879.3 ns/op, 38641 steps/s)**.

CPU top (`go tool pprof -top`, 200k steps, 5550 ms samples):

| flat | flat% | cum% | symbol |
|------|-------|------|--------|
| 2330ms | 41.98% | 85.23% (cum) | `trackmodel.(*TrackWalls).Raycast` |
| 1460ms | 26.31% | | `math.cos` |
| 470ms | 8.47% | | `math.sin` |
| 170ms | 3.06% | | `runtime.preemptM` |
| 70ms | 1.26% | | `trackmodel.clamp` |
| 60ms | 1.08% | | `kinematics.(*AckermannKinematics).Step` |

**Hotspot: raycasting is ~85% cumulative**, and `math.cos`/`math.sin` alone are
~35% flat - the per-ray angle trig is recomputed rather than precomputed per
scan. That is the first optimization target if step time ever matters.

Memory:

- `inuse_space` heap at exit: **~3.2 MB total** (of which ~1.2 MB is
  `pprof.StartCPUProfile`'s own buffer and ~0.5 MB a Windows `NewLazyDLL`
  string - i.e. real steady-state sim heap is well under 2 MB).
- `alloc_space` cumulative: **602 MB over 200k steps, 99.4% from
  `TrackWalls.Raycast`** - one 3072 B scan slice allocated per step
  (matches `3072 B/op, 1 allocs/op`). Churn, not a leak; a reusable scan buffer
  would remove essentially all sim allocation.

### Peak RSS - read this carefully

`go tool pprof` reports **Go heap only, never process RSS**; there is no pprof
command that yields RSS. Measured out-of-band instead:

```powershell
go build -o $env:TEMP\bh.exe ./cmd/bench-harness
$p = Start-Process $env:TEMP\bh.exe -ArgumentList "--steps","200000" -PassThru -NoNewWindow
# poll $p.PeakWorkingSet64 until exit
```

→ **peak working set 50.83 MB.** This is **not comparable to Linux RSS**: the
Windows working set counts mapped shared DLLs. For the §4 comparison the Pi
number must come from `/usr/bin/time -v` (Maximum resident set size) on the
same static binary. Recorded here only so the figure is not mistaken for a
Linux measurement.

## Measured (Python) - _TBD_, NOT RUN HERE

**Python was deliberately not run.** ROS2 is unavailable in this environment
(`ros2` is not on PATH; no ROS2 distro, no `/dev/shm` FastDDS setup). Numbers
are therefore left as `_TBD_` rather than fabricated or extrapolated.

Present here: Python 3.13.14, pixi 0.72.2. Absent: ROS2. So the *sim* profile
below could in principle run under pixi, but the *node* RSS profile cannot.

Target script `platform/robot/scripts/sim/run_scenario.py` exists; flags below
are its real ones (`metadata` positional, `--laps`, `--seed`, `--max-steps`,
`--sighted`).

Ready-to-run on a Pi / CI runner, from `platform/robot`:

```bash
cd platform/robot
SCEN=path/to/scenario_metadata.json   # same fixture both stacks must use
SEED=7

# 1. CPU - cProfile
pixi run python -m cProfile -o sim.prof \
  scripts/sim/run_scenario.py "$SCEN" --laps 3 --seed "$SEED" --sighted
pixi run python -c "import pstats; pstats.Stats('sim.prof').sort_stats('cumulative').print_stats(25)"

# 2. Peak Python heap - tracemalloc wrapped around one scenario run
pixi run python - "$SCEN" "$SEED" <<'PY'
import runpy, sys, tracemalloc
scen, seed = sys.argv[1], sys.argv[2]
sys.argv = ["run_scenario.py", scen, "--laps", "3", "--seed", seed, "--sighted"]
tracemalloc.start()
try:
    runpy.run_path("scripts/sim/run_scenario.py", run_name="__main__")
except SystemExit:
    pass
cur, peak = tracemalloc.get_traced_memory()
print(f"tracemalloc current={cur/1e6:.1f} MB peak={peak/1e6:.1f} MB")
PY

# 3. Process RSS - /usr/bin/time -v ("Maximum resident set size" is in KB)
/usr/bin/time -v pixi run python scripts/sim/run_scenario.py \
  "$SCEN" --laps 3 --seed "$SEED" --sighted 2>&1 | grep -E "Maximum resident|Elapsed|Percent of CPU"

# 4. Per-ROS2-node RSS + CPU - the number that dominates the RSS comparison.
#    tracemalloc/cProfile see ONE process; the real cost is one interpreter per node.
pixi run python - <<'PY'
import time, psutil
names = ("state_machine", "vision", "imu", "lidar", "bridge", "motor_node", "uart_rvc_node")
peak = {}
deadline = time.time() + 60          # sample a live run for 60 s
while time.time() < deadline:
    for p in psutil.process_iter(["pid", "name", "cmdline", "memory_info"]):
        cl = " ".join(p.info["cmdline"] or ())
        for n in names:
            if n in cl:
                rss = p.info["memory_info"].rss / 1e6
                cpu = p.cpu_percent(None)
                cur = peak.get(n, (0.0, 0.0))
                peak[n] = (max(cur[0], rss), max(cur[1], cpu))
    time.sleep(0.5)
total = sum(v[0] for v in peak.values())
for n, (rss, cpu) in sorted(peak.items()):
    print(f"{n:16s} peak_rss={rss:7.1f} MB  peak_cpu={cpu:5.1f}%")
print(f"{'TOTAL':16s} peak_rss={total:7.1f} MB")
PY
```

Also record, for a like-for-like Go comparison: `nats-server` RSS on the Go
side, and the ROS2 daemon + FastDDS `/dev/shm` footprint on the Python side.

## Same corpus / seed / profile - NOT yet apples-to-apples

This is the biggest caveat in this document.

- **Go used a synthetic fixed track, not a corpus scenario.**
  `internal/sim/scenario/bench_test.go` builds a hardcoded 3.0 m square
  boundary with 0.6 m corridor widths and **no obstacles**
  (`Obstacles: nil`, `LidarSeesObstacles: false`), deliberately so the
  benchmark needs no fixture file. `internal/nav/navigator/bench_test.go`
  drives a fake gateway with a fixed clear scan and a synthetic square loop.
- **No seed is shared.** The Go path has no RNG/sensor noise at all; the Python
  path takes `--seed`. There is currently nothing to match.
- **The Python commands above use a real `*_metadata.json` corpus scenario**
  with obstacles and noise - strictly more work than the Go benchmark does.

Therefore: **do not diff the Go ns/op above against the Python numbers when
they arrive.** They measure different workloads on different hardware. To close
this, a true comparison needs (a) the Go harness pointed at the *same*
`*_metadata.json` corpus scenario, (b) the same `--seed` honored on both sides,
(c) the same config profile, and (d) both run on the same Pi. Item (a) depends
on the native Go runner from
`plans/2026-08-30-sim-go-native.md`; until then the Go column is an upper bound
on speed and a lower bound on RSS.
